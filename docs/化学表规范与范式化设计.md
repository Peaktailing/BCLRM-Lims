# 化学域表规范与范式化设计

版本：v1.0 ｜ 日期：2026-10-23 ｜ 适用：`Peaktailing/BCLRM-Lims`（本仓）与 `Peaktailing/BCLRM`（主仓）

---

## 0. 这份文档解决什么问题

两仓都有化学试剂，但表设计走了两条路：

- **主仓 BCLRM**：一张 `reagent_bottle` 三十列，什么都在上面。领用是 `borrow_order` + `borrow_order_item` 两层。
- **Lims（biomanager）**：瓶子是通用库存项 `inventory_items`（二十六列 + `attrs` JSON），化学属性散在 `attrs` 里。领用是 `reagent_borrow_orders` 一张扁平表，**一张单只能一瓶**。

结果是三个具体麻烦：

1. 同一物质的 CAS、分子式、密度，在每一瓶上各存一份，改一次要改 N 行，改漏了就分叉。
2. 一张领用单只能领一瓶，教师要领三样东西得开三张单，审批三次，还不了对不上账。
3. 表名一个复数一个单数（`reagent_demands` / `reagent_demand`），`grep` 找得到但找错对象。

这份文档给出**统一的命名规则**、**瓶主表的范式化目标**、**单据的明细化目标**，以及**从现状迁过去的三段式路径**。核心原则只有一条：

> **主表只留身份；随事件变化的进事件表；被多行共享的进主数据表；外部权威数据独立成表。**

## 1. 命名规则

**规则：`chem_` 前缀 + 单数名词 + 纯小写下划线。**

三条理由：

| 规则 | 理由 |
|---|---|
| `chem_` 前缀 | 化学域在 Lims 里是后加的（C1–C6），与小鼠、质粒、鱼、冻存四个域并列。前缀让「这组表是一起迁的、一起合的」一眼可见，也让将来合仓时能整组定位。 |
| 单数 | 与主仓一致（`borrow_order`、`reagent_demand`）。一行业务一条记录，表名说的是「这行是什么」。 |
| 不带 `reagent_` | 主仓已经用 `reagent_demand` 表示「需求」，Lims 的 `reagent_demands` 结构却不同。留着 `reagent_` 只会继续误导。用 `chem_` 划清边界，语义冲突靠**结构**解决，不靠名字。 |

### 1.1 映射表

| 现状（Lims） | 目标 | 说明 |
|---|---|---|
| `experiment_courses` | `chem_course` | 教学课程 |
| `reagent_borrow_orders` | `chem_borrow_order` | 领用单**头**，去掉 `bottle_id`/`quantity`/`unit` |
| —（新） | `chem_borrow_order_item` | 领用单**明细**，一单一瓶一行 |
| `reagent_return_records` | `chem_return_record` | 归还 |
| `reagent_allocation_orders` | `chem_allocation_order` | 调配 |
| `reagent_demands` | `chem_demand` | 需求 |
| `manager_change_logs` | `chem_manager_change_log` | 保管权流转 |
| `reagent_purchase_plans` | `chem_purchase_plan` | 采购计划 |
| `reagent_purchase_orders` | `chem_purchase_order` | 采购订单 |
| `chemical_experiments` | `chem_experiment` | 实验方案（下一代功能，仅本仓） |
| `chemical_references` | `chem_substance` | **物质主数据**（不是「参考」，改名后语义才准） |
| `controlled_list` | `chem_controlled_list` | 法规管控名录 |
| `notebook_recipes` | **不改** | 属 notebook 域（笔记本里的配方片段），不是化学单据 |

### 1.2 为什么 `notebook_recipes` 不改

它和主仓的 `recipe`（配方聚合根：`recipe_key`/`version`/`status`/组分表）只是名字近似，实际是两个东西。但它是**笔记本文档的一部分**，跟 `notebook_pages`、`notebook_tabs` 一起被版本、分享、协作那套机制管理。改它会把它从 notebook 域里切出来，收益小于代价。合并时由主仓的 `recipe` 吸收，届时整个 notebook 域一起处理。

## 2. `sync_version` 是什么（回答疑问）

**它跟「两台服务器之间同步」没有任何关系。**

Lims 有一个离线客户端能力：手机、桌面 app 可以在没网时继续记账（签试剂瓶、录小鼠体重、写实验记录），联网后合并。为此每张「设备会离线持有一份」的表都带 `sync_version`（`app/sync_clock.py`，注册在 `SYNCED_TABLES`）。

机制是这样的：

```
sync_clock 表只有一行，一个整数，是实验室级的全局变更计数
    ↓ 每次提交，任何一张被同步的表有改动
    ↓ 在同一个事务里 UPDATE sync_clock SET value = value + n
    ↓ 被改的行拿到递增的号，写进自己的 sync_version
```

于是两个问题各有一个答案：

| 问题 | 答法 |
|---|---|
| 我上次看之后变了什么？ | `WHERE sync_version > 我的游标`，加上 `sync_deletions` 里同条件的删除 |
| 我手里这份还是最新的吗？ | 它的 `sync_version` 和我读到的不一样，就说明别人改过——冲突要处理 |

要点在于**计数在写事务内部推进**：PostgreSQL 会把 `sync_clock` 那一行锁到事务结束，所以号是按提交顺序发的，读「大于游标」的客户端不会漏掉「号更小但提交更晚」的改动。SQLite 本来就单写。

### 2.1 为什么 `controlled_list` 有它

注释里写得很直接：**手机签出一瓶试剂之前要查管控名录**（`app/controlled.py` 的 `match()`）。名录在 Configure 里被管理员改过，手机得知道——所以它和别的业务表一样走增量拉取。

### 2.2 主仓为什么没有

主仓是 Streamlit 服务端渲染，浏览器每次都是新请求，没有「设备持有一份副本」这回事，自然没有变更水位。这不是设计缺陷，是两种交付形态的差别。

### 2.3 合表时怎么处理

**保留 `sync_version`，默认 0。** 主仓侧不读不写，Lims 侧的 `sync_clock` 照常给它编号。删掉的代价是 Lims 的 `sync.py` 与 `sync_clock.py` 直接崩，而留着零成本。同理，主仓的 `updated_at` 并进来（默认 `CURRENT_TIMESTAMP`），用于审计列表排序。

这就是 `chem_controlled_list` 的列取并集的原因：

| 列 | 来源 | 用途 |
|---|---|---|
| `id` / `chemical_name` / `alias` / `cas_number` / `dangerous_type` | 两仓共有 | 名录本身 |
| `notes` | Lims | 备注 |
| `sync_version` | Lims | 离线增量拉取 |
| `created_at` | 两仓共有 | — |
| `updated_at` | 主仓 | 审计排序 |
| `UNIQUE(chemical_name, cas_number)` | 主仓 | 名录不重复 |

## 3. 瓶主表：从三十列到「身份 + 三个引用」

### 3.1 三条判据

拆之前先问每一列三个问题，命中哪个就去哪：

| 判据 | 判据问的是 | 去向 | 例子 |
|---|---|---|---|
| **随事件变化？** | 借出一次它就变一次 | 事件表（已有的单据表，或新增） | 余量、启封日、保管人、位置 |
| **被多行共享？** | 十瓶同一种物质，这十行填一样的值 | 主数据表 `chem_substance` | CAS、分子式、分子量、密度、危险性、存储类别、保质期规则 |
| **一批货共享？** | 一次采购到的五瓶，开箱日、有效期、单价一样 | 批次表 `chem_lot` | 供应商、货号、批号、到货日、有效期、单价、包装规格 |
| **都不是** | 只有这一瓶有 | **留在主表** | 编号、所属库、所有者、备注、创建时间 |

### 3.2 目标结构

```
inventory_items                 ← 身份层（通用表，不动结构）
  id, module_id_fk, number, name, ...
  「一瓶一号」= (module_id_fk, number)，number 是模块内自增的 1,2,3…
        │
        │ 1:1（只有化学试剂有这一行）
        ▼
chem_bottle                     ← 瓶子扩展（原来的 attrs 里化学那部分搬到这里）
  item_id_fk PK/FK → inventory_items.id
  substance_id_fk → chem_substance.id    物质是谁
  lot_id_fk      → chem_lot.id           从哪批来
  custodian                               当前保管人（变了写 chem_manager_change_log）
  grade, purity                           这一瓶的实际品级（可能不同于物质默认值）
  opened_on, keeps_months                 启封日 + 启封后能存几个月
  course_id → chem_course.id              课程专用瓶
  state                                   in_stock / borrowed / empty / discarded
        │
        ├── chem_substance   ← 物质主数据（原 chemical_references + 主仓 chemical_info 并集）
        │     name UNIQUE, alias, cas UNIQUE(非空), formula, molecular_weight, mw_source,
        │     density, purity_default, grade_default, hazard, dangerous_type,
        │     storage_class, unsealed_shelf_life, sealed_shelf_life, msds_url, notes
        │
        └── chem_lot         ← 来源批次
              id, substance_id_fk, vendor, catalog_number, lot_no, unit_price,
              produced_on, received_on, expires_on, pack_size, pack_unit

chem_placement                  ← 位置变更（原来直接挂在瓶上的 rack/row/col/note）
  id, item_id_fk, rack_id_fk, rack_row, rack_col, location_note, moved_at, moved_by
```

**为什么位置也要单独成表**：一瓶试剂在生命周期里会被挪很多次（从库房到实验室、从这个柜子到那个柜子）。原设计只记「现在在哪」，历史丢了。而教学实验室恰恰需要回答「这瓶是什么时候被谁放到学生台上的」。

### 3.3 主表瘦身清单（`inventory_items`）

| 现有列 | 判据 | 去向 | 处理 |
|---|---|---|---|
| `id` / `module_id_fk` / `number` | 身份 | 留 | — |
| `name` | 共享 | `chem_substance.name` | 主表留作**快照**（允许一瓶的显示名与其物质名不同，例如「老师给的废液」） |
| `category` | 业务分类 | 留 | 它是模块自定义的，不是物质属性 |
| `status` | 随事件变化 | `chem_bottle.state` | 主表留（其他域还在用），化学侧读写 `state` |
| `owner` / `is_shared` / `share_group_id` | 归属 | 留 | — |
| `quantity` / `unit` | 随事件变化 | 借还流水汇总 | 见 §3.4 |
| `low_at` | 策略 | 留 | 阈值是这一瓶的，不是物质的 |
| `pack_size` | 批次 | `chem_lot.pack_size` | 兼容留 |
| `vendor` / `catalog_number` / `lot` | 批次 | `chem_lot` | 兼容留，写时双写 |
| `rack_id_fk` / `rack_row` / `rack_col` / `location_note` | 随事件变化 | `chem_placement` | 兼容留，写时双写 |
| `received_on` / `expires_on` | 批次 | `chem_lot` | 兼容留 |
| `attrs` 里的 `cas` / `purity` / `grade` / `hazard` / `keeps_months` | 共享 | `chem_substance` / `chem_bottle` | 回填后不再新写 |
| `attrs` 里的 `opened` / `custodian` / `course` | 随事件变化 | `chem_bottle` | 回填后不再新写 |
| `notes` / `created_at` / `updated_at` / `updated_by` | 独有 | 留 | — |

### 3.4 余量为什么不能只是「一列」

现在是 `quantity` 一个数字，借出时减、归还时加。问题有三个：

1. 减错了没有依据可以追——只知道现在是多少，不知道为什么会变成这个数。
2. 分装（一瓶倒成两瓶）、损耗、过期报废都会改这个数，但改法不同。
3. 跨量纲换算（44 g 的需求对上 500 mL 的瓶子）需要密度，而密度在物质上。

处理：**余量作为流水的结果，不作为独立事实。**

```
期初（chem_lot.pack_size，入库时的量）
  − Σ chem_borrow_order_item.issued_qty
  + Σ chem_return_record.quantity
  ± chem_allocation_order（分装：转出方减、接收方加）
  − chem_scrap（报废/损耗）
  = 当前余量
```

第一段实施时不建流水表，而是建一个**视图** `v_chem_bottle_state` 把「主表 + 物质 + 批次 + 最近一次事件」拼成原来的扁平形状（§5.2）。等读路径都切过去了，再决定是否需要物化。

## 4. 领用单：从「一单一瓶」到「一单多瓶」

### 4.1 现状的问题

```sql
reagent_borrow_orders
  bottle_id, quantity, unit      ← 挂在单头上
```

一张单只能一瓶。教师上「有机化学实验」，要领无水乙醇、水杨酸、乙酸酐三样，就得开三张单、走三次审批、记三个到期日。归还时对账更麻烦：哪张单还了、哪张没还，要逐张看。

### 4.2 目标

```
chem_borrow_order                   头：谁、为什么、什么时候还、批没批
  id, number, requester, approver, status,
  purpose, course_id, experiment_name, due_at, remark,
  sync_version, created_by, created_at, decided_at

chem_borrow_order_item              行：哪瓶、要多少、发了多少、还了多少
  id, order_id_fk → chem_borrow_order.id ON DELETE CASCADE,
  item_id_fk → inventory_items.id,
  quantity, unit,                 申请量
  issued_qty,                     实发量（可与申请量不等：库存不足）
  returned_qty,                   已还量
  state,                          pending / issued / partial / returned / short
  remark
```

这张结构跟主仓的 `borrow_order` + `borrow_order_item` **语义对齐**，只是列名和粒度不同（主仓用 `bottle_number` 文本，Lims 用 `item_id_fk` 外键）。将来合并时可以直接映射，不需要重写逻辑——这正是本仓「结构冲突但可映射」的设计意图。

### 4.3 兼容处理

`chem_borrow_order` 上的 `bottle_id` / `quantity` / `unit` **暂时保留**，含义降级为「单瓶简式」：单一明细时它的值与唯一明细行相同。新增的单据只写明细，旧单据读时若明细为空，就按旧列合成一行（视图 `v_chem_borrow_order_line` 负责这件事）。

### 4.4 与两段管线的接点

主仓新建的两段管线（教师→管理员承接 / 管理员→管理员平账）落到 Lims 时：

| 两段管线概念 | Lims 落点 |
|---|---|
| `Acceptance.issued` 每行 | 一条 `chem_borrow_order_item`（`state='issued'`） |
| `Acceptance.shortfalls` 每行 | 一条 `chem_borrow_order_item`（`state='short'`，`issued_qty=0`） |
| `TransferProposal.lines` 每行 | 一条 `chem_allocation_order`（`from_holder` → `to_holder`） |
| 缺口单（`recipe_key + ':gap'`） | 头表的 `purpose` 记「平账：<原单号>」，明细照抄 |

`state='short'` 让「没领到」成为**可查询的事实**，而不是靠「单据状态是 borrowed 但数量不够」去推断。

## 5. 迁移路径：expand → migrate → contract

改名的同时改结构，一步做完必然炸。分三段：

### 5.1 第一段：expand（本次实施）

只做加法，一个旧列都不删、一个旧名都不留坑：

1. Alembic `0050_chem_tables_normalised`
   - `RENAME TABLE` 旧名 → 新名（`has_table(旧) and not has_table(新)` 时执行）
   - 建 4 张新表：`chem_borrow_order_item`、`chem_lot`、`chem_bottle`、`chem_placement`
   - `chem_substance` 补列：`alias`、`density`、`purity_default`、`grade_default`、`dangerous_type`、`storage_class`、`unsealed_shelf_life`、`sealed_shelf_life`、`updated_at`
   - `chem_controlled_list` 补列：`notes`（已有）、`updated_at`、唯一索引
   - 回填：`attrs` 里的化学字段 → `chem_substance`；每瓶一条 `chem_bottle`；每瓶一条 `chem_placement`（当前位置）
2. `models.py` 的 `__tablename__` 同步改名，新表按 ORM 定义
3. `0045` 的 `TABLES` 列表改新名（它从 `metadata` 取结构，名字不更新会 KeyError）

**为什么改 `0045` 是安全的**：新装库走 `create_all()` → `metadata` 已是新名，`0045` 用新名建表；老库已 stamped 在 0049，不会再执行 0045。历史迁移的**语义**没变（表结构依然只来自 models），变的只是一个查表用的字符串。

### 5.2 兼容视图（降低切换风险）

```
v_chem_bottle_state     主表 ⋈ chem_bottle ⋈ chem_substance ⋈ chem_lot
                        投影出原来的扁平列（cas / purity / grade / custodian / opened /
                        vendor / lot / received_on / expires_on / …）
v_chem_borrow_order_line  明细 ÷ 旧单瓶列，统一成「一单一瓶一行」的旧形状
```

读路径可以先继续读视图，逐步替换成直接读新表。视图里不写逻辑，只做拼接。

### 5.3 第二段：migrate（下一步）

- 读路径从视图切到新表（`reagent_workflow.py`、`inventory_service.py`、`chemical_experiments.py` 的用量统计）
- 写入双写：写旧列时同时写 `chem_lot` / `chem_placement` / `chem_bottle`
- 增加一致性自检：比对「旧列」与「新表投影」是否相等，不等就报

### 5.4 第三段：contract（合仓前）

- 删除 `inventory_items` 上的化学专属 `attrs` 键与冗余列
- 删除 `chem_borrow_order` 上的 `bottle_id` / `quantity` / `unit`
- 删除兼容视图

## 6. 两仓对照

| 概念 | 主仓 BCLRM | Lims（本仓） | 合并时 |
|---|---|---|---|
| 瓶子 | `reagent_bottle`（30 列） | `inventory_items` + `chem_bottle` | Lims 侧已有身份/属性分离，主仓需要拆 |
| 物质 | `chemical_info`（14 列） | `chem_substance`（17 列） | 并集，以 `chem_substance` 为骨架 |
| 管控名录 | `controlled_list`（7 列） | `chem_controlled_list`（9 列） | 已取并集，见 §2.3 |
| 领用 | `borrow_order` + `borrow_order_item` | `chem_borrow_order` + `chem_borrow_order_item` | 列名映射即可 |
| 归还 | `return_record` | `chem_return_record` | 同上 |
| 调配 | `allocation_order` + `allocation_order_item` | `chem_allocation_order` | Lims 需补明细（分装多瓶） |
| 需求 | `reagent_demand` + `reagent_demand_item` | `chem_demand` | Lims 需补明细 |
| 采购 | `purchase_plan` + `purchase_plan_item` / `purchase_order` | `chem_purchase_plan` / `chem_purchase_order` | 主仓的用量推算式可并入 |
| 课程 | `experiment_course` | `chem_course` | 主仓多学期/班级/专业/学院 |
| 实验方案 | `experiment_plan`（6 列文字） | `chem_experiment`（21 列） | 主仓无对应物，Lims 独有 |
| 配方 | `recipe` + `recipe_component` | —（`notebook_recipes` 是别的东西） | 主仓独有 |
| 地点 | `reagent_bottle.storage_location` | `chem_placement` | 主仓需补历史 |

### 6.1 结构冲突是刻意的

用户已明确：`chem_experiment` 与 `experiment_plan`、`notebook_recipes` 与 `recipe` 属于**下一代功能**，两仓结构冲突是可接受状态，现在不统一。本轮只处理**基础功能**（借还、调配、采购、物质档案、管控名录）的名字与结构。
